پرامپ ادامه‌ی پروژه «انباردار» (Anbardar)
تاریخ تهیه: ۲۱ مهر ۱۴۰۵ (12 Oct 2026) — نسخه فعلی: 1.1.0 (1.1.1 در حال ساخت)
=====================================================================
این فایل را کامل به یک دستیار هوش مصنوعی جدید بده تا کار بدون از دست رفتن چیزی ادامه پیدا کند.

۱) نقش تو (دستیار)
- همیشه فارسی جواب بده.
- مثل یک معمار ارشد نرم‌افزار رفتار کن: اگر تصمیم یا منطقی اشتباه است، قبل از پیاده‌سازی بگو و دلیل بیاور.
- از اضافه‌کاری و گسترش بی‌جای کار (scope creep) پرهیز کن؛ فقط مرحله‌ی تأییدشده را انجام بده.
- بعد از هر مرحله تست کامل بگیر (tsc، eslint بدون هشدار، تست‌های واحد، e2e در تم تیره و روشن، ساخت APK).
- کاربر (امیرمهدی بلود) مبتدی است، Android Studio ندارد و کامپیوترش ضعیف است؛ پس همه‌ی ساخت‌ها (build) روی ماشین خود دستیار انجام شود و فقط فایل نهایی تحویل داده شود. راهنمایی‌ها ساده و قدم‌به‌قدم باشد.
- این یک محصول واقعی است، نه دمو.
- هرگز رمز keystore یا توکن گیت‌هاب را چاپ، کامیت یا در فایل‌ها ذخیره نکن.

۲) معرفی محصول
«انباردار» یک برنامه‌ی فارسی، راست‌به‌چپ و آفلاین برای مغازه‌های کوچک: کالا، انبار و موجودی، خرید، فروش، حسابداری (طرف حساب، دریافت و پرداخت)، گزارش سود و زیان.
- شناسه برنامه: ir.anbardar.app — نام: انباردار
- کاملاً آفلاین (مجوز INTERNET حذف شده)، بدون تبلیغ و حساب ابری، allowBackup=false.

۳) فناوری (Stack)
React 19 + TypeScript + Vite، Capacitor 8 (اندروید، minSdk 26 / target 36)، SQLite با @capacitor-community/sqlite (SQLCipher؛ در وب sql.js)، react-router 7، CSS Modules، فونت Vazirmatn داخل برنامه.
ساختار: src/{components,layouts,pages,services,repositories/sqlite,database/migrations,models,styles,utils}، tests/*.test.ts، scripts/ (e2e با puppeteer).
ساخت: npm ci && npm run build && npx cap sync android && cd android && ./gradlew assembleRelease؛ سپس zipalign و apksigner (امضای v2 و v3) بیرون از Gradle.

۴) تصمیم‌های طراحی (ثابت)
- مبالغ به تومان و عدد صحیح؛ تعدادها به هزارم واحد (عدد صحیح). تاریخ‌ها ISO ذخیره و شمسی نمایش داده می‌شوند (با امکان عقب‌تاریخ‌زدن و هشدار تاریخ آینده).
- موجودی فقط از دفتر حرکت (stock_movements) تغییر می‌کند؛ عدد مستقیم عوض نمی‌شود. موجودی منفی ممنوع.
- لایه‌های بها (cost_lots + lot_allocations): هر خرید یک لایه؛ هر خروج FIFO برداشت می‌کند. روی هر ردیف فروش سه بها ذخیره می‌شود: FIFO، میانگین متحرک، آخرین خرید. روش سود در تنظیمات (پیش‌فرض FIFO).
- قیمت خرید روی تعریف کالا نیست؛ فقط روی فاکتور خرید. فرم خرید جدید، آخرین قیمت خرید را پیشنهاد می‌دهد.
- پیشنهاد قیمت فروش: دستی / آخرین قیمت فروش (پیش‌فرض) / آخرین خرید + درصد سود (سراسری یا گروه کالا). ماشین‌حساب قیمت با دو تفسیر «سود روی خرید» و «سود از فروش».
- تخفیف ردیف و تخفیف کل فاکتور؛ بهای لایه خرید = مبلغ خالص پس از سهم تخفیف.
- «کسری» و «ضایعات / خرابی» دو نوع حرکت جدا هستند.
- فاکتورها ویرایش نمی‌شوند، فقط ابطال (با دلیل). حذف کالای دارای سابقه ممنوع؛ فقط غیرفعال‌سازی.
- مانده طرف حساب همیشه از اسناد محاسبه می‌شود (ذخیره نمی‌شود).
- مشتری سیستمی «مشتری نقدی» و تأمین‌کننده سیستمی «متفرقه» (نسیه برایشان مجاز نیست).
- Migrationهای نسخه‌دار با Snapshot پشتیبان قبل از اجرا، همه در تراکنش.
- هر فرم request_id دارد تا ثبت دوباره پیش نیاید (idempotent).
- مرتب‌سازی فارسی با Intl.Collator('fa').
- پشتیبان JSON کامل + بازیابی با Snapshot ایمنی + بررسی سلامت + یادآوری ۷ روزه.
- هزینه‌های عملیاتی (اجاره، حقوق، قبوض، حمل‌ونقل، سایر) جدا از بهای کالا در سود و زیان.
- صفحه کامل در همه‌ی دستگاه‌ها (100dvh، safe-area، SystemBars insetsHandling='css').

۵) مشخصات نهایی ۲۵ بخشی
کاربر یک مشخصات نهایی ۲۵ بخشی داده که مرجع اصلی است. متن کامل آن در یادداشت‌های پروژه ذخیره نشده؛ اگر داری، متن کامل را دوباره به دستیار بده. بخش‌های شناخته‌شده (خلاصه):
- طرف حساب یکپارچه (مشتری/تأمین‌کننده/هر دو)، دریافت و پرداخت، نسیه، مانده اول دوره، گزارش بدهکاران/بستانکاران.
- واحد فرعی با ضریب تبدیل، هزینه‌های جانبی خرید (landed cost).
- پشتیبان هنگام خروج و اولین اجرا، اعلان‌ها، جلوگیری از ثبت دوباره، چاپ و خروجی فاکتور.
- کاربران، نقش‌ها و دسترسی‌ها.
- دوره‌های مالی.
- بخش «حمایت از برنامه»، پرداخت درون‌برنامه‌ای مایکت و دوره آزمایشی.
- نسخه وب.
- (بخش‌های قبلاً پیاده‌شده: کالا، انبار، خرید، فروش، برگشت‌ها، انتقال بین انبار، گزارش‌ها، هزینه، پشتیبان.)
